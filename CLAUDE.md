# Project Guidance

## Review diffs

- Focused local and GitHub pull-request review plans should include bounded, prioritized full-file text context when available so unchanged lines above and below a hunk remain expandable.
- Preserve the patch-only fallback for binary, oversized, unavailable, or non-UTF-8 file contents.

## Pull request workspace

- A pull request opens in `PullRequestWorkspace` (`components/github/workspace/`), keyed by profile so it stays mounted while pull requests change. It holds the queue rail, the per-pull-request `PullRequestReviewView` (loading and error states included), the shortcut bar, the leave guard and the active tab.
- Tabs are Overview, Conversation, Tour and Code. A pane mounts on first visit and then stays mounted (hidden) so drafts, scroll and review state survive tab switches. The tab is owned by the workspace (`tab` / `onTabChange`), so it is kept when switching pull requests.
- `PullRequestDetailHeader` (in `PullRequestDetailTabs.tsx`) is shared by the loaded and loading views and is one row of the same height on every tab, so the tab strip never moves. The status sits beside the tabs (hidden on Overview, whose verdict band already says it). The author, commits, branch and diff-size line is `PullRequestMeta`, rendered at the top of Overview and Conversation, which share one left-aligned column on the header's 24px edge.
- Every way out of the open pull request (rail, J/K, back, close, title-bar tabs, deep links, profile switch) goes through `requestLeave` in `pullRequestLeaveGuard.tsx`. Anything holding typed, unsaved text reports it with `useReportUnsavedText`; `ReviewView` reports through `onUnsavedTextChange`.
- The rail (`rail/PullRequestListRail.tsx`) is the whole inbox with the inbox's own groups and `pullRequestStatus`; do not fork that logic. It is a tree with one tab stop. Its visibility is remembered separately for reading tabs (Overview, Conversation; open from 1240px) and code tabs (Tour, Code; open from 1840px, since beside a diff it costs 280px of code); below 1240px it floats.
- Keyboard has three owners and one helper (`shortcuts/pullRequestShortcuts.ts`): the workspace dispatcher (`pullRequestWorkspaceKeys.ts`: J/K pull requests, H/L tabs, `/`, Mod+B, `?`) listens on `window` and skips `defaultPrevented` events; `ReviewView` owns `[` `]` `V` arrows `C` Escape and Mod+F (forwarded from `body`, a pull request tab or the rail by `forwardOutsideDiffKey`, since React only delivers them inside its section); the Tour owns ←/→ and R. Every handler calls `preventDefault` on keys it handles. A focused tab strip or list keeps only its arrow keys (`ARROW_OWNERS`); letters such as R still reach the Tour. Escape closes a floating rail from anywhere unless something else handled it. The bug scan view counts as an open overlay (`OVERLAY_SELECTOR`). Letters fire only without a modifier; punctuation is matched by `event.key` so Shift and AltGr layouts work. `pullRequestShortcutList.ts` is the one list behind the bar and the dialog.
- Keyboard switching selects the row at once and loads after 150ms; neighbours are prefetched into the same detail cache. Do not add work to `PullRequestReviewView` that re-renders it while the rail selection moves.

## Pull request Overview and Conversation

- Overview is a decision page in this order: Merge status, Risk level (or "From the author" without a tour), Issues, Behavior changes. When nothing is open (no unresolved thread, no open local finding) Behavior changes comes before Issues, so the first screen is not spent on an empty list. The description lives in Conversation; Overview shows only its clamped start when there is no tour.
- The merge verdict, its fact strip and the "Before this can merge" checklist come from `overview/pullRequestMergeVerdict.ts`, built on `pullRequestMergeBlockers`. The header status renders the same verdict. Its test is the copy table: change wording there. A pull request that still needs an approving review is never ready.
- Check groups (Failed, Running, Passed, Skipped) come from `detail.checkRuns`, a field of its own because the inbox row is spread over the detail and overwrites `checks`. One `checkOutcome` in `github.ts` drives both the counts and the runs so they always add up.
- Issues are review threads (`overview/pullRequestReviewThreads.ts`). A current thread opens Code at the thread; an outdated one opens Conversation at the comment. Bug scan findings are a separate "Local scan · not posted" group and never count as unresolved threads. Resolving stays on GitHub.
- Behavior changes lists only tour steps of `kind: 'behavior'`.
- AI-written text always ends with a provenance line (which head, when) and never looks like a GitHub fact. Writing or rewriting a tour always goes through `BackgroundJobConfirm`.
- Merging sends the head SHA on screen (`GitHubPullRequestMergeInput.headSha`); GitHub rejects it when the branch moved.
- The revision on screen is the one acted on. The inbox row reaches the detail only through `overlayLivePullRequest` (`pullRequestLiveDetail.ts`): never its `headSha`, its `checks` and counts only for the same head, and only a row at least as new as the detail (never the click-time prop). A fetched detail with a new head or base is held back by `pickShownDetail` while text is unsaved or review drafts are pending (drafts are stored per head), with a notice saying what to finish. `loadGitHubPullRequestDetail` reads the metadata again once `/files` has loaded; a load whose reads do not all name one head and base is thrown away and retried once (`pullRequestLoadDescribesOneRevision`). `/files` deliberately still loads in parallel with the first read (holding it back cost 0.2–0.4s per cold open). The review plan IPC takes head and base and refuses a revision other than the last one loaded.

## Pull request Tour and Code

- Tour and Code share ONE `ReviewView`. The tab only changes `fileScope`, `sidebar` and `progressLead`, so viewed state, the open composer, the line cursor and review continuity exist once. Never mount a second instance for a pull request. While a composer is open, switching between Tour and Code or changing step is refused with a notice.
- In the pull-request layout `ReviewView` shows files, not Blocks (`ReviewFilesView.tsx`, `reviewFileScope.ts`): a files panel (filter, tree with `+/−` and a viewed tick, Show menu, unified/split), every file stacked in one scroller with sticky headers and a Viewed checkbox, and a progress strip. Local branch reviews (`layout="standard"`) keep Blocks and J/K.
- Hunks prepare, highlight and mount only near the viewport (or when a jump targets them) and then stay mounted. Every jump (`navigationRequest`, tree, `[`/`]`, thread, search) mounts its target first, then scrolls.
- Files hidden by review filters stay in the tree dimmed; opening one reveals just that file. Coverage counts files across the whole plan and never counts a hidden file as viewed. Scope (whole pull request vs since last review) lives in the Show menu. A tour step's files are never hidden by filters or scope.
- Viewed is per file (all of its chunks). A step's Reviewed is the Tour's own state (`tour/pullRequestTourWalk.ts`, stored per pull request, head and tour generation) and never ticks files.
- One AI run writes the tour and Overview's risk text. Tours are stored with `version: 3` (a before/now `change` per step, a short `label` per point, an optional `flow`; no `questions`); an older stored guide reads as `outdatedFormat`. Validate model output in `src/shared/pullRequestTour.ts` rather than trusting line numbers: a point is trimmed to one hunk of the loaded plan, a point that cannot be placed stays as text with a null anchor, every changed file is owned by exactly one step, risk is never defaulted to low, over-long text is clipped at a sentence or word (`clipText`), and a flow is kept only where it names code (a non-context node names a step point or a changed file, at most two context nodes each joined to one that does, no cycles, at least three nodes with two naming code; otherwise `null`).
- The prompt (`buildPullRequestTourPrompt`) states word budgets, the JSON shape and one worked example step; change wording there and in the validation limits together. The tour uses each harness's flagship (`TOUR_PI_MODEL` with high thinking, the `opus` alias in the Claude fallback); other Pi jobs keep the fast default.
- The step panel is for scanning, not reading: risk, title, Before/Now, the call to make (copper rule), the flow (`TourFlow`, rows top to bottom from `layoutTourFlow`; an edge that skips a row takes a side lane so no line runs behind a box), the footprint (each file a +/− bar with its points placed where their lines fall) and one headline per point. A point's sentence is shown only beside its lines in the diff, at a fixed height (selection only changes the fill, so scroll sync never moves code); a point that cannot be placed keeps its sentence in the panel. Every number in these pictures comes from the plan (`tourVisuals.ts`), never from the model.
- Progress segments are as wide as the changed lines they stand for (each hunk counted once, for the step whose point lands in it, else the file's owner; log scale, `tourSegmentWeight`), underlined amber or red for medium or high risk, with a copper diamond for a call to make. **Map** beside the strip opens `TourStepMap`: every step's volume, risk, call and reviewed state; ↑/↓ move, a row opens its step. A tour written before the latest push, or for another base (`baseSha`, recorded since a retarget keeps the head), uses `unanchorTourPoints` (no line marks).
- Points and code stay linked in both directions: selecting a point jumps to and tints its lines (`navigationRequest`); the copper number in the diff selects the point. In Code the same points appear inline labelled `step.point`.
- The Tour is the only AI layer in the pull request view: pass its points to `ReviewView` as `guideReferences` and do not pass `reviewGuideProvider` there (the AI brief is for local reviews). Pi is the default harness; fall back to the Claude Code CLI only when Pi is missing or signed out, never to hide real Pi failures.
- Tour prose renders through `GuideProse`: inline code naming a changed file (full path or unique suffix such as `machines.ts`) becomes a borderless file link that scrolls to it; other inline code keeps the tinted code style.

## Pull request status

- Count only unfinished check runs (and PENDING/EXPECTED status contexts) as pending in `parseChecks`; skipped and neutral runs are derived as `total - passed - failed - pending` and never shown as pending.
- Merge conflicts are actionable: `categorizePullRequest` files conflicting authored PRs under `needs-action`, and `pullRequestStatus` ranks conflicts above Draft so a label never hides them.
- Overview lists merge blockers (conflicts, failing or running checks, changes requested, draft, behind, approval required, branch rules) in `PullRequestMergeChecklist`, each with the action that clears it (`pullRequestMergeBlockers.ts`). Status wording is shared: `PULL_REQUEST_STATUS_LABELS` in `pullRequestInboxStatus.ts` feeds both `pullRequestStatus` (inbox, rail) and the merge verdict (header, Overview), so one state never reads two ways. Waiting for someone else's approval is pending blue. "Ready for review" calls `gh pr ready` and must never run without the user's click.
- Recently pushed branch lookups that fail with 403/404/410/422 are permanent and never raise the inbox warning; Retry clears the suggestion cache first. The inbox states what it includes and how many matches GitHub left out (`omittedCount`).

## Line breakdown

- Classify changed lines by path only in `src/shared/lineBreakdown.ts`; the Code tab's `categorizeReviewPath` and `isGeneratedReviewPath` live there too, so both views agree.
- The inbox gets at most 100 files per pull request from GraphQL; show the remainder as `Unlisted` rather than dropping it. The detail header uses the detail's full `files` list.
- Inbox rows and the detail header show it in the same hover/focus table on the `+/−` totals (`PullRequestLineStats` with `breakdown`); don't add an always-visible split line, it was too cluttered.

## PR accessibility

- AI jobs (tour, bug scan) never start from a single click: idle or outdated jobs open `BackgroundJobConfirm` first. Inbox rows keep the job state icon-only (details in the tooltip); words beside the icons were tried and read as clutter. A job that has not run shows the plain icon: the status dot appears only for ready, running, outdated or failed, so a dot always means there is something to look at.
- Inbox J/K move focus between rows (Enter opens) while focus is in the list or nowhere. In an open pull request J/K switch pull requests.
- Busy controls (refresh, Write tour, reviewer options) use `aria-disabled` plus a guarded click instead of `disabled`, so keyboard focus stays put.
- Announce background status changes (tour ready/failed, refresh failed, new activity, the pull request or tour step that opened) through `src/renderer/src/lib/announce.ts`, the single polite live region.
- Single-key shortcuts only act while focus is inside the pull request workspace or on `body`, never from an input, menu or dialog, and only while the "Single-key shortcuts" toggle in the shortcuts dialog is on (WCAG 2.1.4).

## PR visual tokens

- Stylelint (`.stylelintrc.json`, part of `pnpm lint`) requires `font-size` to use `--text-*` and `border-radius` to use `--radius-*`; mark a real exception with a `stylelint-disable-next-line` comment that says why.
- Use the `:root` type, spacing, and tone tokens in `main.css` for PR surfaces; keep content text at 11px or larger (10px only for counts, pills, and eyebrows).
- Tones: `pending` = in progress (info blue), `warning` = needs attention (amber), `muted` = no signal. Do not use amber for pending.
- In the Tour, teal marks position (the step strip, the current step, the selected tab and rail row) and copper (`--guide-annotation`) marks the tour's own commentary (point numbers, attention heads). Point numbers are only for real code↔point references, and both directions must stay linked. Risk chips: low muted, medium warning, high danger; none when unassessed. Merged PRs use the neutral `merged` tone with a merge icon, not success green.
- Custom fields use `--border-control` at rest and the `.form-input:focus` treatment (`--focus-ring` border plus 1px outline) on focus; `--border` and `--select-border` are too faint for field edges or focus (WCAG 1.4.11).
- No content text below 11px anywhere, dashboards and Portainer included (`--text-2xs` stays for counts, pills, eyebrows and avatar initials).
- States that can last minutes (running CI runs, the "N Running" pill, tour writing) use the static `CircleDotDashed` icon or a dashed ring; spinners are only for short fetches, and skeletons are static.
- Pull request status glyphs come from one set, `PullRequestStatusIcon` (named by `PullRequestStatusIconName` in `pullRequestInboxStatus.ts`): each state has its own shape (conflict, draft, changes requested, failing, awaiting review, waiting, blocked, approved, ready, merged, closed), shared by the inbox, the rail, the header and Overview. Do not map a status to a generic triangle or dot in a component. The rail and the inbox row lead with the glyph in a 22px tile tinted with its tone. Merged is the neutral tone; violet (`--ai-text`) is for AI output only.
- Icons in pull request surfaces use three sizes: 12 beside meta text, 14 in controls, tabs and rows, 16 for standalone header buttons, closes and section verdicts (20 in empty states; 10 only for external-link marks). `.btn-regular` sets 14px.
- Pull request tabs and Overview's Issues tabs are text tabs with count pills and one teal underline that slides to the selected tab (`useSlidingIndicator`: measured, slides only on a selection change). Do not bring back the segmented track. The rail's selection is one highlight that slides the same way (`placeRailHighlight`).
- Loading keeps its shape. `PullRequestReviewLoading` renders the real header with stand-ins at the real sizes for Refresh, Review, Merge and More, the known tab counts and placeholders for the unknown ones, so nothing in the header moves on arrival; when a loaded control changes size, change its stand-in with it. The skeleton mirrors the remembered tab (and a collapsed Tour panel) and fades out toward the bottom (a static mask, no shimmer). The inbox's first load is `InboxSkeleton`, whose rows use `.pr-inbox-row` itself so the grid cannot drift. `PullRequestLoadPhase` is the one "still loading" line in the header. A pull request that replaces its skeleton fades in once (`data-arrived`, cleared when the fade ends); a cached one, a tab switch and a new head appear at once. A hunk that is not mounted yet shows static code-line placeholders (`.review-stack-placeholder`).
- The workspace's overall look is decided in `styles/pr-surface.css` (loaded last): panels (rail, files tree, tour panel, inbox nav) share the canvas and are separated by a divider, never a lighter slab; the header, tabs, progress strip, panel content and reading column share one 24px left edge; Overview's sections sit on the canvas between single hairlines, and the merge verdict is one band tinted by its tone (the only filled object on the page); reading prose is `--text-base` (14px), tour prose 13px. One solid teal button is on screen at a time: Merge on Overview and Conversation while the verdict is Ready to merge (neutral but still clickable otherwise, so the loudest control never contradicts the band), the panel's finishing action on Tour and Code (`quietMerge`). Review is always a neutral button.
- Motion says what just happened or where you moved, once. CSS entrances live in `styles/pr-motion.css`; script-started ones use `lib/motion.ts` (`EASE_OUT`, `drawStroke`, `useDrawOnBecoming`, `prefersReducedMotion`). Rules: nothing loops, nothing animates on a background poll (`PullRequestRefreshControl` spins and pings only for a refresh the user clicked or for new activity), nothing replays on mount, tab return or navigation (checks are drawn from the state change, not from CSS), every one-shot is under 400ms (the clicked refresh glyph turns at most three times), flags that arm a one-shot are cleared by a timer rather than by `animationend` (which never fires under reduced motion or `display: none`), a placement that must not slide commits its position before the transition is allowed again, and reduced motion turns all of it off.
- A shortcut lights its key cap in the shortcut bar only when it did something: handlers call `shortcutUsed(chip)` after the action is accepted (`go`, `advance`, `stepFile`, `toggleViewed` report it). Never infer it from `defaultPrevented`.
- Electron's "Error invoking remote method" prefix is stripped once in the preload `invoke` (`src/shared/ipcErrors.ts`), so `error.message` is safe to show.


## Workflow run graph

- A job card's look comes from `workflowJobState` (`workflowJobState.ts`). Failed and running are the only filled cards (red, info blue), queued is the blue outline without the fill, passed stays flat and neutral, skipped is dashed. Don't add fills, shadows or weight to passed cards, and never change font weight by state: a heavier name wraps differently and the graph re-flows when a job fails.
- The sidebar and the header tally list jobs by state with failed first (`groupWorkflowJobsByState`). Tally chips for failed, running and queued jump to the next job in that state. Passed is a plain count.
- Opening a run scrolls the graph to its failed jobs, or its running ones when nothing failed. The graph scrolls inside `.workflow-run-job-scroll`, so the run facts and tally stay put.
- Geometry lives in `workflowRunGraphLayout.ts`, which places cards and lines in one coordinate space. Every column is packed from the top in workflow order (collapsed skipped jobs last). Don't reorder or align cards to straighten lines: that was tried and read as a mess. Density is fixed (6px gaps, columns only as wide as their longest name), so never fix clutter by adding space.
- Don't draw every dependency at rest. With the columns packed it is a tangle however it is routed. At rest only the failure flow is drawn (`workflowFailureFlow`): what each failed job held up, in red, and what the first failure of a chain waited for. Hover or focus on a card draws everything it waits for and everything waiting on it, and dims the rest.
- Tracing must not move anything. Pinned lines get their own tracks and set the gutter widths; traced lines fit into the tracks and gaps that are left (`pinnedEdges` and `tracedEdges` in `computeWorkflowGraphGeometry`).
- The lines that can be drawn are the dependencies a longer chain does not imply (`reduceWorkflowJobDependencies`). With skipped jobs collapsed, a job that ran links to the nearest jobs that ran before it, so a collapsed skipped node ends lines and never relays one.
- A dependency that skips columns passes through the gap between two cards or below the column, never behind a card. Lines merge on a vertical track only when they share a job.

## Selection and profiles

- List selection follows the macOS rule: the focused list shows `--select-row-focused` (teal tint), every other list `--select-row` (neutral). Graph rows, the sidebar tree and the PR inbox nav switch with `:focus-within` on their container; keep new lists on the same tokens.
- The PR inbox nav lists only All / Review requests / Yours and repositories; status categories narrow from each group heading's Show only button, never a second copy in the nav.
- The profile menu (`ProfileMenu.tsx`) only switches profiles. The editor lives in `ProfileEditor.tsx` inside Settings › Profiles (`ProfileSettingsSection.tsx`); `onOpenProfileSettings` opens Settings scrolled there.

## Diff readability

- Syntax themes are readable copies registered in `src/renderer/src/components/diff/diffTheme.ts` (`git-gud-dark-plus`, `git-gud-tokyo-night`). `READABLE_COLORS` lifts token colours to 4.5:1 on the `.gg-diff` canvas, added/removed lines and word emphasis; comments only need 4.5:1 on lines so they stay dimmer. Re-derive the map whenever the canvas, line tints or emphasis alphas in `main.css` change.
- Pierre pairs the n-th removed and added lines of a block; `dissimilarLineDiff.ts` drops word emphasis when a pair shares under half its words, so unrelated lines are not painted with confetti.
- The `codeFontFamily` setting (Settings › Diffs › Code font) overrides `--font-mono` on the document root; the name is sanitised in `normalizeCodeFontFamily`.

## Pull request review comments

- Keep new line and file comments local until the user submits the review. While a submission is in flight (`pullRequestReviewSubmission.ts` records it per draft storage key, so a reopened view sees it too) the same drafts cannot be submitted, edited or removed, and posted drafts are cleaned from storage before the key is released.
- Render line composers and threads beneath their diff line; do not move active commenting UI above the diff.
- Pierre's gutter utility stays off for large-review hover performance (6489996); hovering a line number shows a CSS `+` and selecting lines opens the composer. Keyboard users get the line cursor in `reviewLineCursor.ts` (PR layout): ↑/↓ move, Shift extends within one chunk, C opens the composer for the range, Escape clears it. `[`/`]` move between files and V marks the current file viewed.
- Normalize dragged line ranges into ascending GitHub API order regardless of drag direction.
- Keep file, step and filter navigation disabled while a comment composer is open so typed text cannot be orphaned. Viewed is disabled on a file with an open composer, and collapsing a file never discards typed text.
- In the pull-request layout Escape never closes the PR: it dismisses an empty composer (typed text needs Cancel). Closing or adding a comment returns focus to the review so J/K/V keep working.
- Use `btn-regular` for 32px review/header actions, `btn-compact` for 28px composer actions, and `review-comment-action` for 24px tertiary comment controls.
- Publish whole-file comments with GitHub's `subject_type: file` API and omit line fields.
- Only expose published-comment editing for comments authored by the active GitHub viewer. GitHub remains the authorization source of truth.

## Other machines (view-only)

- Never run a command on another machine that can write: keep `GIT_OPTIONAL_LOCKS=0`, and only use status, for-each-ref, and diff reads over SSH. No stage, commit, checkout, or context-menu actions on machine rows.
- Mirror remote branches only into local `refs/machines/<id>/heads/*`, and only inside `gitExecutor.transaction` plus `runDuringRefMutation`, so watchers don't loop.
- Machine WIP rows use `machine-wip:<id>` shas, carry `machineWip`, and never set `worktree`.
- Validate SSH hosts with `SSH_HOST_PATTERN`; a leading `-` must stay impossible.
- Tailscale discovery only runs `tailscale status --json` (`src/main/tailscale.ts`); check the app bundle and Homebrew paths because Finder-launched apps have a minimal PATH. Adding a device saves its full MagicDNS name after a passing connection test, and offers "Add anyway" on failure.
- Keep the last snapshot when SSH fails and show it as stale; changing a machine's SSH host clears its cached snapshot.
- Machine diffs pin `--src-prefix=a/ --dst-prefix=b/` so a remote `diff.mnemonicPrefix` or `diff.noprefix` cannot make patches unparseable.
